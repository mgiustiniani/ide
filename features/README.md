## Status and profile semantics

- Every production scenario owns one repository-unique `@REQ-*` ID, at least one requirement classification, and exactly one effective status.
- A status is a product implementation declaration, not a summary of every supporting test result. Focused fixtures, adapter tests, or protocol probes do not change it.
- `@implemented-and-validated @web` scenarios run through the Playwright web profile. The current selection contains two scenarios: `REQ-WEB-001` and `REQ-LAYOUT-WEB-001`.
- `@implemented-and-validated @desktop @native-gui` scenarios run through the explicit `desktop/tauri-webdriver` profile. The current selection contains exactly three scenarios: `REQ-LAYOUT-DESKTOP-001`, `REQ-DESKTOP-FILE-OPEN-001`, and the bounded deterministic `REQ-REFACTORKIT-JAVA-IMPORT-002`. Layout evidence is limited to the release/no-bundle Linux X11 WebView DOM at an asserted 1440x900 viewport, with no OS decoration, package, Wayland, DPI-behavior, drag-resizing, restart-persistence, or optional-right-sidebar claim. The other native requirements retain their separately stated evidence boundaries.
- `@implemented-not-e2e-validated @desktop` scenarios run through the deterministic `desktop/tauri-harness` aggregate. It currently selects `REQ-REFACTORKIT-JAVA-IMPORT-001` and `REQ-XCOM2-MACHINE-SETTINGS-001` and provides no native GUI/E2E evidence. The XCOM machine Settings lifecycle is separate from future XCOM project/module activation and carries no native GUI, real IPC, live Steam, real filesystem, package, bundle, or installer claim.
- `@not-implemented` scenarios are excluded from implemented aggregates. The current count is three: `REQ-REFACTORKIT-TS-001`, `REQ-REFACTORKIT-TS-002`, and `REQ-XCOM2-MODULE-ACTIVATION-001`.
