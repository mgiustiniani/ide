**Evidence status:** **RESEARCH / FROZEN / NEEDS-REVIEW.** The bounded capability research remains tied to its stated cut-off. Repository-status observations are historical unless explicitly reconciled below; use [ARC42](../ARC42.md) for current implementation evidence.

**2026-07-14 roadmap freeze:** this document is not an active roadmap. Definition/references, symbols/hierarchy, code actions, formatting, rename, Java module activation, contextual Java tooling, general refactoring, and broader JDT LS expansion are unscheduled TODO until a relevant released RefactorKit capability passes immutable real acceptance validation. ## A. Scope and methodology

This is a capability-domain analysis, not a trademark or compatibility claim. JetBrains now presents IntelliJ IDEA as one unified product with a free core and an Ultimate subscription for advanced tooling; entitlement, bundled-plugin state, operating system, selected runtime, and product version still change what a user sees ([product overview](https://www.jetbrains.com/idea/features/), [comparison](https://www.jetbrains.com/products/compare/?product=idea&product=idea-ult), [discovery guide](https://www.jetbrains.com/help/idea/discover-intellij-idea.html)). “Ultimate” below means capabilities documented as advanced/enterprise or traditionally subscription-gated, not that every row is exclusively Ultimate in every release.

IntelliJ IDEA is versioned and extensible. Literal parity is not a finite target: Marketplace plugins, private plugins, evolving AI/cloud services, and arbitrary external tools cannot be exhaustively inventoried. This document inventories the major built-in and Ultimate product domains documented by JetBrains as of the cut-off; it does **not** claim every Marketplace plugin.

Method:

1. Review current official JetBrains product pages, the 2026.1 Help site and its sitemap; prefer official sources and summarize rather than copy them.
2. Separate platform/general IDE (`Core`), Java-specific (`Java`), advanced/enterprise (`Ultimate`), bundled or separately installed plugin (`Plugin`), and runtime/tool-dependent (`External`) concerns.
3. Inspect repository code and existing documentation, especially [Java IntelliSense Plan](JAVA_INTELLISENSE_PLAN.md), [ADR 0005 and 0006](../ADR.md), and current C4 views.
4. Classify each target under one of five provider classes defined in section D. A provider class is an implementation boundary, not a promise that an open-source substitute has JetBrains-equivalent depth.

### Evidence and edition caveats

Inline source groups such as **[S-Java]** resolve to the official source appendix. All listed sources were reachable or redirected to a current official page on 2026-07-11. JetBrains can move pages and change edition boundaries after that date. Features implemented by bundled plugins (for example framework, database, Docker, Kubernetes, AI, collaboration, or language plugins) must be capability-probed rather than inferred from a product name. External servers, JDKs, CLIs, credentials, browsers, containers, database drivers, and profilers remain operational dependencies.

### Repository baseline established by inspection

- **Files/workspaces:** workspace-scoped file operations, stable workspace metadata/registry, switching, tabs and persisted editor state exist through ports/adapters. Browser storage is a constrained simulation; desktop uses authorized native paths.
- **Editor:** local Monaco 0.52.2 is the only editor. It is lazy, model-per-file, uses same-origin workers, and bundles a Java Monarch/basic language contribution. No-file state is a Kate-style create flow; loading is source-free; failure offers Retry Monaco with no native fallback.
- **Java tree semantics:** conventional Java source roots are recognized; package-only chains compact only below those roots while retaining the deepest real path. Production/test presentation and the Maven icon exist. This is presentation, not a complete JDK/build project model.
- **Terminal:** xterm.js UI exists. Desktop executes bounded, non-interactive, one-shot programs; web output is simulated. There is no persistent PTY/job-control terminal despite terminal-like presentation.
- **Pi agent:** an optional desktop Pi RPC integration has typed contracts/adapters, settings/status/install, command discovery, prompts, workspace-scoped session restoration, and persisted run traces. It is not JetBrains AI Assistant and does not imply AI completion, cloud model, or autonomous edit parity.
- **Global Java Settings:** Settings > Java owns JDK/JDT LS lifecycle/status and RefactorKit availability/version/path. Fixed guarded RefactorKit scan/query/navigation handlers and authorized-location parsing exist natively, but those project actions are not exposed globally.
- **JDT LS:** managed lifecycle, versioned document synchronization, diagnostics/Problems projection, and the interactive completion/hover/signature-help/cancellation slice are implemented. Provider-neutral contracts, typed Tauri adapters, bounded Rust/LSP transport, and guarded Monaco providers serve only the exact synchronized Java model. Workspace/session/path/URI/version/request/cancel guards, optimistic versions, serialized `didChange` flush-before-request, and stale/late suppression are enforced. Completion applies only its primary edit; additional/workspace edits and commands are suppressed. Markdown is untrusted/HTML-disabled, and managed configuration enables signature help. No Java module activation or full contextual project-tool lifecycle exists. Browser has no Java tab or hidden Java polling.
- **Paste Java Class from Clipboard:** the desktop directory tree implements a directory context action and tree-focused `Ctrl/Cmd+V`, capability-before-clipboard coordination, complete preview presentation, exact-plan acknowledgement/approval/apply, discard on cancellation/invalidation, and backend-result refresh/open. Rollback exists in contracts, adapters, Rust, and provider authority, but the import UI has no rollback action. Installed RefactorKit `0.5.0-SNAPSHOT` (API `0.2`) provides `bin/refactorkit-daemon`; Rust manages one NDJSON process per canonical workspace generation and kills it on malformed output, timeout, workspace switch, or app exit. It does not intercept editor paste, infer packages, write project content directly, log source, or send source/plan/transaction data to Pi. Older/incomplete providers remain unavailable before clipboard read. Provider open may create `.refactorkit/workspace.lock`, so preview/no-write means no imported-target or other project-content write before Apply, not complete hidden-tree identity.

### Current RefactorKit audit buckets

- **Current IDE capability:** provider status/capability discovery and the managed Java external-class import transaction, with deterministic harness evidence kept separate from provider and native/package evidence.
- **Parked for confirmed defects:** TypeScript diagnostics and saved-snapshot semantic navigation. Neither support code nor deterministic fixtures override the observed protocol/runtimes failures.
- **Working provider foundation, IDE TODO:** structural outline and identifier search.
- **Experimental provider foundation, IDE TODO:** TypeScript references and proposal-only rename, plus other operations advertised experimental.
- **Unsupported/unintegrated TODO:** general Java refactoring beyond import and unsupported TypeScript/JavaScript format/move/organize-imports/change-signature/extract/inline operations.

Announced RefactorKit search operations with optional JSON remain TODO until a released capability exposes strict typed bounded versioned machine-readable JSON, or an equivalent daemon DTO, with structured errors, truncation, authorized locations, request/result correlation, and immutable real acceptance evidence. Human-oriented stdout must never be parsed as an IDE protocol.

Java support is therefore not one feature. It is a project model plus an interactive semantic engine, deterministic graph/transformation engine, toolchain adapters and native workflow UI. Ultimate-class framework depth cannot be obtained merely by starting JDT LS; proprietary JetBrains models and years of edge-case behavior remain a real competitive gap.

## D. Provider decision framework

### D1. Classifications

1. **`IDE-native UI/state`** — Monaco presentation, panels, navigation history, keyboard UX, diffs, settings, trust prompts and local recovery.
2. **`Language service`** — JDT LS/LSP for latency-sensitive, document-version-aware completion, hover, signature, diagnostics, symbols, hierarchy, definitions/references and quick actions.
3. **`RefactorKit-like deterministic engine`** — safe, repeatable cross-file analysis and preview/apply/rollback based on a reproducible workspace snapshot.
4. **`External tool adapter`** — Maven/Gradle/Ant, JDK/jdb/JDWP/DAP, test runners, Git, Docker/Kubernetes, databases/drivers, servers and profilers.
5. **`Hybrid`** — explicit orchestration across at least two providers, retaining provenance and authority.

### D2. Frozen Historical Provider-Fit Inventory for RefactorKit-Like Tooling

- deterministic workspace scans and versioned symbol-graph snapshots;
- exact definitions/references fallback and auditable evidence;
- preview/apply/rollback for rename class/member/local, move, safe delete, signature changes, extract method and organize imports;
- structural search/replace, recipes and codemods;
- framework-aware migration and risk detection;
- dependency/API upgrade recipes with unresolved-use reporting;
- architecture rules and batch inspections suitable for local use and CI;
- multi-file edit validation using canonical paths, document versions, file hashes, transaction journal and crash recovery.

The IDE must probe actual RefactorKit capabilities rather than infer them from a version. Installed `0.5.0-SNAPSHOT`/API `0.2` implements the bounded external-class transaction, but this list remains a backlog rather than a claim that the provider implements every operation. Older or incomplete installations stay unavailable without force or fallback.

### D3. Frozen Historical Non-RefactorKit Provider Fits

Text editing/rendering, cursors, selection and keymaps; low-latency completion/hover/signature and document synchronization; debugger protocol/UI; terminal/VCS UI; database browser/query console; container/cloud clients; build/test execution itself; profiler sampling/rendering; and AI chat/session transport. Using RK for these would add latency, stale-state risk, inappropriate coupling, or duplicate a standard external protocol.

### D4. Retained Safety Arbitration (Not Active Scheduling)

| Capability   | Primary                                                   | Secondary/arbitration                                                                                        | Why                                                                         |
| ------------ | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| Diagnostics  | JDT LS for open-document live findings                    | RK for explicit scan, deeper batch and CI. Show provider; dedupe only stable same-range/code/message matches | Live diagnostics need unsaved versions; batch findings need reproducibility |
| Code actions | JDT LS for local quick fixes tied to diagnostics/version  | RK for supported multi-file or policy transformations; always preview multi-file edits                       | Avoid stale edits and preserve deterministic safety                         |
| Imports      | JDT LS for add/import candidate during typing             | RK for organize imports, repository-wide normalization and CI                                                | Different latency and repeatability needs                                   |
| Rename       | RK for supported preview/apply transactions               | JDT LS may offer preview fallback only when RK lacks capability; never merge edits; user sees provider       | Rename is safety-critical and cross-file; RK can hash/journal               |
| References   | JDT LS for cursor-driven, cancellable interactive results | RK for exact selector, snapshot evidence, fallback and cross-check                                           | Unsaved buffers favor LS; audit/repeatability favors RK                     |
| Definition   | JDT LS for cursor/dependency source                       | RK for exact workspace definition fallback/evidence                                                          | Same split; existing selector workflow remains useful                       |
| Inspections  | JDT LS for edit loop                                      | RK for architecture/batch/CI; framework plugins add separate provenance                                      | “One Problems list” must not hide different authorities                     |

Global rules: results carry provider, workspace generation and document/snapshot version; stale results are discarded; providers are never silently merged; conflicting edits force recomputation/user choice; all multi-file apply operations reauthorize paths and hashes; provider failure degrades only that capability.
