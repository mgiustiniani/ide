# ARC42 — IDE Architecture Documentation

## Section 1: Introduction & Goals

### 1.1 Requirements Overview

The IDE is a three-panel Integrated Development Environment:

1. **Left sidebar** — accordion navigation with File Explorer above Workspace Explorer; both sections expand and collapse independently.
2. **Right/center area** — Monaco-only editor for opening and editing files.
3. **Bottom panel** — a dynamic accessible tool-window host. Desktop contributes core Terminal and AI Agent tools plus a conditional project-scoped Problems tab for the current Java context/diagnostics; web contributes core Terminal only.

**CURRENT/AS-BUILT — 2026-07-16:** within application content, the activity rail and left sidebar span the full available height; the bottom shell/tool-window host belongs only to the narrower editor-side column and does not extend beneath navigation. Top-level chrome/status remains separate and stable through panel changes. The optional right sidebar remains inside the editor row and is responsively bounded. Keyboard resizing and accessible separator semantics remain available for the left and bottom panel boundaries. When the whole sidebar is collapsed, an accessible expand control persists in the activity rail; the bottom-panel toggle persists in the status bar in both visibility states. Desktop shell wiring routes both controls to layout state without clearing retained panel dimensions. The web and desktop declarations are now both `@implemented-and-validated`, with distinct target-specific evidence.

It runs as a **Tauri 2.x desktop application** and is reusable as a **standalone webapp** with no Tauri dependency.

Workspace Explorer lists every registered workspace and owns workspace switching, refresh, loading, and error feedback. The former duplicate workspace selector in the header has been removed. File Explorer compacts package-only namespace chains only beneath recognized Java source roots. It preserves the deepest real node/path, distinguishes production `src` and test folders, gives `pom.xml` a dedicated Maven icon, and leaves unrecognized directory hierarchies unchanged.

Monaco Editor 0.52.2 is the only file editor. It is bundled locally with same-origin workers, one model per file, and a Java Monarch/basic language contribution. Lazy activation waits for a visible, renderable, positive-area active-file host before mount and timeout; layout reruns after visibility returns. No-file state is a Kate-style create flow. Loading uses an inert source-free placeholder, and import/runtime failure offers Retry Monaco with no native fallback. No CDN or CSP expansion is required.

The implemented Java baseline has two desktop foundations. **Settings > Java** exposes only global full-JDK/JDT LS lifecycle/status and RefactorKit availability/version/path/capability discovery. Managed JDT LS now provides provider-neutral lifecycle, versioned document-sync, diagnostics, completion, hover, signature-help, and cancellation contracts; typed Tauri adapters; fixed no-shell Rust/LSP transport with isolated per-workspace data; and guarded Monaco providers. Fixed native RefactorKit Java scan/query/navigation handlers exist, but their project actions remain unexposed globally. Browser mode has no Java technology tab or hidden Java polling.

Interactive diagnostics, completion, hover, signature help, and cancellation operate only for the exact synchronized Java model. Workspace/session/path/URI/version/request/cancel guards, optimistic versions, serialized full-text `didChange` flush-before-request, and stale/late suppression protect the flow. Current diagnostics feed Monaco and a conditional project-scoped Problems tab; that visibility guard is not Java module activation. Completion maps only its primary edit; additional/workspace edits and commands are suppressed. Documentation is untrusted Markdown with HTML disabled, and managed configuration sets `java.signatureHelp.enabled=true`.

**2026-07-14 roadmap policy:** preserve and maintain this as-built lifecycle, synchronized-document flow, diagnostics/Problems projection, completion, hover, signature help, cancellation, and stale guards. Further IntelliSense or JDT LS expansion is removed from the active roadmap until a relevant released RefactorKit capability passes immutable real acceptance validation. Definition/references, symbols/hierarchy, code actions, formatting, rename, Java module activation, the full contextual Problems/Build/Tests/Logs lifecycle, general Java refactoring, and other contextual Java tooling are **UNSCHEDULED TODO / FROZEN HISTORICAL INVENTORY**, not milestones or target architecture. Unsupported or unintegrated capabilities are never simulated.

One bounded IDE workflow is implemented separately: **Paste Java Class from Clipboard** is available from a selected directory's context menu or `Ctrl/Cmd+V` while the directory tree owns focus; editor paste is not intercepted. Its coordinator capability-probes before an explicit clipboard read, presents complete backend placement, affected-file, rendered/structured-diff, risk, diagnostic, provenance/license, conflict, staleness, and blocker evidence, requires acknowledgement for unknown/high-risk provenance, applies only the exact approved ready plan under workspace/selection generation guards, displays the backend transaction, and refreshes/opens backend-reported paths. Rust manages one canonical-workspace, generation-scoped `bin/refactorkit-daemon` NDJSON process and supports preview, exact-plan apply, discard, and backend transaction rollback. Compatibility is provider-version-neutral: API 0.2 plus the required import/apply/discard/rollback method features authorize the current Java-import boundary; provider version is diagnostic only. Language-kernel and top-level safety metadata are strictly normalized and retained when advertised, but the four safety booleans may be absent and do not all gate current Java-import authorization. The IDE never parses or copies raw Java in presentation code, infers a package, writes files directly, falls back to target-package, logs source, or sends source/plan/transaction data to Pi. RefactorKit is the imported-project-content writer and rollback authority, but the current import UI has no rollback action. Missing or incomplete required method capability remains unavailable before clipboard read. See the [current Java boundary and frozen inventory](docs/JAVA_INTELLISENSE_PLAN.md); the retained research does not claim IntelliJ IDEA Ultimate parity.

## Section 2: Constraints

### 2.1 Technical Constraints

- **pnpm workspace** — all packages live under a single monorepo.
- **Vite** — both `apps/web` and `apps/desktop` use Vite as the build tool.
- **Tauri 2.x** — desktop target requires Rust and Tauri CLI.
- **No Tauri imports in shared packages** — `packages/ui/`, `packages/web-core/`, `packages/contracts/` must not import `@tauri-apps/api`.
- **External Java import authority** — only a managed RefactorKit advertising API 0.2 and the required import/apply/discard/rollback method features may preview and apply a `targetDirectory` import or provide backend rollback. The IDE must not infer support from version, top-level safety metadata, or language-kernel discovery; convert a directory to target-package; or write a fallback patch. The current import UI has no rollback action.
- **Clipboard privacy** — capability probing precedes clipboard access; the clipboard is read only for an explicit directory-tree action and is never routed to Pi. Normal editor paste remains independent.
- **Read-only semantic navigation** — saved-snapshot search/definition must execute no project script and produce no workspace change, including hidden provider metadata. Advertised `writesWorkspace:false` is evidence to verify, not permission to tolerate a contradictory lock write.
- **XCOM recognition authority** — convention scanning is limited to the current authorized Linux workspace through a dedicated native metadata/name command. Exact-case regular entries are evidence; symlinks are neither traversed nor accepted. The fixed depth-8, 20,000-encounter, and heavy-directory exclusions are not caller-configurable.
- **XCOM activation configuration authority** — the native side alone owns `<authorized-workspace>/.ide/xcom2.json`. It accepts only activation-only v1 under strict 64 KiB, UTF-8, duplicate-key, schema, 1–64-root, exact-case, regular non-symlink, and canonical containment rules. Exactly eight safe codes may cross into fixed presentation; no raw project/native detail may cross. The IDE has no XCOM configuration/evidence write or `.gitignore` mutation authority and rereads only on explicit full Workspace Refresh. Normal application-owned `.ide/workspace.json` marker/registry metadata is outside that project-input no-write scope.
- **Project Foundry authority** — one shared Rust in-process `git2` renderer is the sole Preview output authority and returns the complete plan body/internal bytes. TypeScript strictly validates the closed result and byte consistency, computes the digest, and owns immutable approval/presentation custody; web core owns no template source/output or parallel renderer. Fake selectors remain harness-only and provide no native chooser claim. The current production slice is Linux-only, read-only, process-free, and has no Apply transaction or creation authority.

## Section 6: Runtime Architecture

### 6.1 Startup Sequence

1. **Entry point** (`main.tsx`) mounts the React root and the app shell instantiates its runtime adapters.
2. **App component** (`App.tsx`) initializes stores and composes ten application controllers plus six extracted shell/document/editor controllers. Workspace-scoped controller auto-loads are deferred.
3. **Workspace authorization transition** starts at positive generation 1. The Workspace controller awaits `ensureCurrentWorkspace`; no registry read or dependent native workspace read may overtake it.
4. **Registry promotion** lists the registry after authorization and promotes the ensured workspace over a stale or empty snapshot.
5. **Dependent activation** begins only after the authorized root and promoted registry are current: editor restore, file-tree load, Java attach/status load, workspace-keyed AI activation/commands, RefactorKit status/capability discovery, and one jointly correlated XCOM convention scan plus fixed-path activation-v1 read run under the shared generation. With Settings closed, startup still performs no XCOM machine monitor, history, detail, poll, or subscription work.
6. **Panel layout** renders full-height activity/sidebar navigation beside an editor-side flex column. The editor row owns the main editor and optional responsively bounded right sidebar; the lower column owns the bottom resize boundary and tool host. Status and desktop top-level chrome remain outside application content. A collapsed sidebar remains recoverable from the activity rail, and the status bar keeps the bottom visibility toggle available; both desktop requests flow through the Desktop Shell Controller without resetting stored dimensions. BottomPanel descriptors retain icon/title/scope/badge/disabled/active metadata and accessible tab/tabpanel keyboard behavior.
7. **Sidebar navigation** renders independently collapsible File Explorer and Workspace Explorer sections; Workspace Explorer lists registered workspaces and handles switching/refresh/errors, while File Explorer derives Java-aware presentation only below recognized source roots.
8. **Editor** renders a no-file create state or source-free loading placeholder; only a visible, renderable positive-area active-file host may start Monaco import/mount and timeout, followed by layout when visibility returns. Failure offers Retry Monaco.
9. **Terminal** setup is workspace independent and may proceed during root authorization; web shows a simulated session and desktop executes submitted commands one at a time.

If initial authorization fails, dependent workspace activation does not run, loading settles, and presentation receives a sanitized error. A later user switch invalidates an older cold-start attempt and advances the generation before collaborator reset/detach.

### 6.2 Workspace Switch Flow

1. Advance `WorkspaceGeneration` before asynchronous detach or native switch work.
2. Reset Editor and RefactorKit Import state; stop/invalidate RefactorKit Symbol Navigation; invalidate Java, RefactorKit Status, AI Agent, and any open-Settings XCOM lifecycle through narrow collaborator interfaces.
3. Detach the old Java session, then invoke the serialized native workspace switch only if the generation is still current.
4. Attach/activate the returned authorized workspace, clear shell previews/terminal state, and reload registry, file tree, Java, AI Agent, and RefactorKit status/capabilities. XCOM starts one correlated convention scan plus activation-v1 read for project recognition. If Settings remains open, it separately starts one fresh monitor/transaction lifecycle; if closed, it performs no machine-runtime work. Failed restoration may restart only one current open-Settings lifecycle.
5. Suppress any completion whose generation/request/workspace identity is stale. On current failure, restore only the bounded collaborators that define restoration behavior.

### 6.3.1 Native Desktop File-Open Flow

1. The selected native profile first executes `pnpm --filter @ide/desktop tauri build --no-bundle --ci`, verifies the fixed release executable, and records its SHA-256; an environment override cannot substitute an older binary.
2. The runner creates one temporary sandbox and redirects `HOME`, all configured XDG state roots, `IDE_HOME`, the authorized workspace, and temporary roots beneath it. It removes inherited display/session variables, then starts an isolated D-Bus session and X11 Xvfb display.
3. `tauri-driver` starts `/usr/bin/WebKitWebDriver`, which launches the real Tauri WebView and freshly built release/no-bundle ELF. The accessible File Explorer exposes the deterministic root item.
4. After click, one shared 15-second deadline covers exact selected path, exact selected accessible tab, and exact Monaco logical content. Opening/failure placeholders and file-open alerts must be absent; a separate bounded browser probe establishes responsiveness.
5. Closing the native window must remove the observed executable process within five seconds. Cleanup deletes the WebDriver session, stops the owned driver/application processes, and the Story verifies expected workspace metadata/content plus canonical containment of redirected state roots.

The first real run exposed a production state-publication defect: `TauriEditorAdapter.getOpenFiles()` returned its mutable adapter-owned array by alias, so startup restore and consumer mutation prevented the first tab from being published. Commit `9b4af2a` returns defensive array/object snapshots from get/open/close and adds the native-like controller regression. The subsequent real native Story passed 16/16. This flow proves one Linux X11/Xvfb direct file open only; it does not prove package installation, Wayland/other-OS behavior, arbitrary host-filesystem non-mutation, or other editor workflows.

### 6.4 RefactorKit Native Foundation and Managed Daemon Flow

Fixed Rust handlers validate explicit Java selectors and authorized workspace-relative locations. The `refactorkit_daemon.rs` Tauri facade delegates transactional import to application, capability-policy, contract, path-policy, and transport modules. The transport launches `bin/refactorkit-daemon` directly without a shell and owns one NDJSON process per workspace generation. The application service validates API 0.2 and required import/apply/discard/rollback method features without authorizing from provider version, opens the canonical workspace, correlates requests, normalizes rich preview output, applies only the exact `planId`, invokes `refactor.discard` on cancellation/invalidation, and provides backend rollback by transaction ID. It also normalizes and retains language-kernel and safety metadata when advertised; the top-level safety booleans are evidence, not a complete Java-import authorization gate. The import UI does not expose rollback. Malformed protocol output, timeout, workspace switch, and application exit kill the process; bounded logs exclude source text.

The separate saved-snapshot semantic module is implementation-informed support for a parked TypeScript/JavaScript requirement: it can start a capability-gated session with explicitly approved external tools, search workspace symbols, resolve a selected opaque identity to a provider point, and stop under exact workspace/generation/session/snapshot authority. Desktop composition contains a generic Search integration, but the immutable real provider contradicts the required no-write behavior during `project.open`; deterministic protocol success must not hide that defect or promote the workflow to a current IDE capability. Broader fixed RefactorKit project actions remain unintegrated. Any announced search stdout is non-contractual and must not be parsed.

### 6.5 Paste Java Class from Clipboard Flow

1. The developer selects a directory and invokes its context action or presses `Ctrl/Cmd+V` while the tree owns focus. Editor paste is not intercepted.
2. The coordinator validates workspace/directory selection and probes `java.importExternalClass`; failed, absent, target-package-only, or incomplete required method capability stops with no clipboard read or write.
3. Only a provider advertising API 0.2 plus `targetDirectory`, preview, apply, discard, and rollback method features triggers one explicit clipboard read. Top-level language-kernel and safety fields are retained when present but do not independently authorize this read. Empty/oversized text is refused; source remains transient and never reaches Pi or logs.
4. RefactorKit alone produces the complete correlated plan. Refused/error/stale plans retain backend evidence for review but cannot apply. Conflicts, blockers, ineligibility, changed workspace/selection, or missing required provenance acknowledgement disable Apply; cancel/invalidation calls `refactor.discard`.
5. Approval binds the exact displayed `planId` and current generations. Apply sends only plan/workspace/workspace-generation/selection-generation/request identity plus the plan-bound approval; the IDE neither resends source/patch/target data, infers a package, reconstructs edits, nor writes directly.
6. A successful backend result supplies the opaque transaction, changed files, and primary file used for display, exact parent refresh, and primary-file opening. Backend rollback exists by transaction ID through RefactorKit, but there is no current user-facing rollback action.

### 6.8 XCOM 2 Recognition, Machine Monitor, Dry Run, and Transaction Runtime

```text
Authorized workspace activation → correlated convention scan + fixed activation-v1 read
  → strict Tauri validation + dedicated Rust metadata/name/configuration boundaries
  → pure convention/configured evaluation with separate confidence fields
  → exact safe-code mapping → one complete atomic Workspace warning
  → diagnostic alone: no activity; strong Option A: activity mirrors complete warning
  → recognition-only activity or no contribution
Explicit full Workspace Refresh → clear warning/decision → neutral checking → reread/rescan → stale suppression
Committed switch → synchronous recognition revocation → stale result suppression

Distinct empty prelaunch HOME/XDG/IDE/workspace locations
  → visible Settings navigation → App composition → typed Tauri monitor adapter/invoke → Rust monitor
  → exact accessible missing-Steam presentation only

Settings closed → no XCOM snapshot/refresh/history/detail/poll/subscription work
Settings opened → one monitor subscription/poll lifecycle → one fresh snapshot
                → one transaction subscription/poll lifecycle → one history load
Manual refresh → one monitor refresh + one additional history load
Settings close → synchronously revoke authority → unsubscribe both → clear both timers
Reopen/open switch/failed restore → at most one fresh workspace-correlated lifecycle

Desktop Settings → separate pure dry run (always non-executable)
                 → transaction history/review/full digest/controls
                                      │
                                      ▼
Native engine: write intent → backup by content hash → atomic mutation → verify
                                      │
                           reverse rollback / recover
```

The recognition controller and machine Settings controller are independent. Workspace activation and explicit full Workspace Refresh jointly correlate one bounded convention scan and one fixed-path configuration read for the current authority; opening or closing machine Settings neither supplies recognition/diagnostic evidence nor controls project activity. Refresh synchronously clears the prior diagnostic and decision, exposes neutral checking, and accepts results only when workspace, activation, configuration, and scan identities/generations still match. Option A contributes roots with two distinct convention kinds; valid activation v1 may independently contribute configured/explicit roots while recognition confidence stays separate. Invalid configuration removes configured authority but does not suppress strong Option A. Exactly eight safe codes map to one complete atomic warning in **Settings > Workspace > Current workspace**; a diagnostic creates no activity, while independently surviving high-confidence Option A retains its activity and mirrors that warning. `needs-confirmation` and inactive roots contribute nothing. Recognition creates no bottom tab or action. The IDE writes neither `.ide/xcom2.json`, Option A evidence, nor `.gitignore` and starts no configuration/evidence watcher or poll. Normal application-owned `.ide/workspace.json` marker/registry metadata is outside this XCOM input no-write scope.

The Settings lifecycle contributes no project recognition. Lifecycle identity plus workspace/generation/request guards reject stale snapshots, histories, details, events, and late responses. The 27/27-step deterministic evidence exercises the production `App`, controllers, and typed adapters over fake IPC effects and time; it is not native GUI, real IPC, live Steam/filesystem, or package evidence.

Approval binds the transaction, workspace, monitor generation, ordered operations, and preconditions. Before mutation, the engine rejects stale hashes/generations, path escapes, workspace mismatches, duplicate targets, and invalid journal digests. Every checkpoint is durable; rollback traverses applied steps in reverse and refuses to overwrite conflicting post-apply changes. Recovery can verify a journal, resume interrupted rollback, or retry conflict-safe rollback when observable state permits.

For the concrete SDK flow, Prepare fingerprints the stable Steam game/SDK roots, captures exact baseline evidence, and constructs the fixed 15-operation set. Apply revalidates that evidence and requires the exact complete digest for one transaction. Restore Vanilla SDK traverses applied steps in reverse, restores exact bytes/modes/inventory or original symlink absence, and refuses conflicting overwrites. A successful restore permits Prepare Again.

Synthetic fixtures prove repeat apply→rollback cycles, restart recovery, and conflict-safe retry. The live Prepare audit reported 15 operations, executable, and no blockers; no live Apply occurred. Protontricks, Steam shortcut, prefix, package-manager, and interactive setup remain FUTURE/TARGET and cannot enter this transaction.

## Section 8: Cross-Cutting Concepts

### 8.1 State Management

- **Zustand** stores in `packages/web-core/state/`.
- Each panel has its own store slice (file tree, editor, terminal, panel layout).
- Stores are platform-agnostic; adapters update store values asynchronously.

### 8.2 Styling

- **Tailwind CSS** utility classes for layout and theming.
- Shared Tailwind configuration lives in `packages/ui/tailwind.config.ts` and is consumed by app builds.
- Light/dark colors are defined with CSS variables; the app currently renders with the dark class.

### 8.3 Error Handling

- Adapters catch platform errors and map them to user-facing error messages or typed adapter errors.
- View models expose loading and error state for UI handling where implemented.

### 8.4 Security

- Desktop: Tauri uses the default capability and a Content Security Policy; Rust commands constrain file paths to the workspace and reject shell chaining, raw shells, executable paths, long-running commands, and oversized output.
- Monaco and all editor workers are local same-origin assets; the editor adds no CDN dependency and requires no CSP expansion.
- Webapp: runs in the browser sandbox and stores simulated workspace data in `localStorage`.
- Managed JDT LS: Rust authorizes workspace paths, discovers known external tools, starts JDT LS without a shell, isolates per-workspace state, and bounds messages/events/restarts/cleanup. Exact-model workspace/session/path/URI/version/request/cancel guards and flush-before-request ordering prevent stale or cross-model results. Completion suppresses additional/workspace edits and commands; Markdown is untrusted with HTML disabled. Browser adapters report Java providers unavailable rather than simulating results; a remote provider would require explicit opt-in and a separate ADR.
- External Java clipboard import: target validation and authoritative API/method-feature probing occur before clipboard access. Language-kernel and top-level safety metadata are validated and retained when advertised but are not all authorization gates. Unsupported, stale, refused, blocked, mismatched, or failed work stops without fallback. Clipboard source is transient, goes only to RefactorKit preview after support is proven, and never reaches Pi. Exact-plan acknowledgement/approval, backend-owned mutation and non-UI rollback authority, and backend-authoritative refresh/open paths prevent the IDE from manufacturing project-content writes. Preview does not guarantee byte-identical hidden metadata because provider open may create `.refactorkit/workspace.lock`.
- RefactorKit TypeScript diagnostics: discovery metadata and a pure readiness decision do not authorize native invocation or rendering. Until the protocol carries exact authority/correlation, compiler attestation, complete ranges, and current editor-snapshot identity, exact Monaco markers and full existing-surface projection fail closed.
- RefactorKit TypeScript/JavaScript symbol navigation: capability evidence, explicit external-tool paths, saved-buffer checks, authority correlation, transient opaque identity, and exact point validation fail closed. A full hidden-file byte-tree audit is required because immutable `v0.6.2` writes `.refactorkit/workspace.lock` during nominally read-only `project.open`; advertised `writesWorkspace:false` does not override observed mutation or authorize it. Option A parks the slice until read-only `project.open` and semantic navigation do not write the workspace, or until the provider capability/contract is corrected and separately approved.
- JDT LS and the full JDK are external, non-bundled tools under separate licenses. The pinned JDT LS release is installed/verified with `pnpm tools:install-jdtls` and `pnpm tools:verify-jdtls`.
- Native layout/file-open Stories: the runner forces a fresh release/no-bundle build and isolates D-Bus/X11. Each scenario support session acquires a distinct contained environment lease for HOME/XDG/IDE/temp/workspace/evidence roots, including its own `IDE_HOME`, then restores the runner environment and removes the child root. This prevents `.ide` and workspace state from crossing between those native scenarios; it remains bounded test isolation, not a global host-filesystem audit.
- XCOM 2 Settings: runtime work is permitted only while Settings is open. Close revokes lifecycle/request authority before synchronously unsubscribing both typed adapters; their final unsubscribe clears poll timers. Workspace/generation correlation prevents stale switch/restore completion from restoring authority. Native monitor reads are bounded to fixed Steam AppIDs. Separately, bounded native acceptance reaches the exact accessible missing-Steam state through visible Settings navigation and the natural App/Tauri/Rust path from isolated empty prelaunch locations; this is presentation-only evidence with no IPC instrumentation/counting, lifecycle/polling, refresh/reopen, planning/transaction, activity/tool, mutation/post-launch-filesystem, live-Steam/machine-correctness, package, or broader-platform claim. The concrete SDK transaction is constrained by the captured Steam/root fingerprint, exact-digest one-transaction approval, local machine journals/backups, path/hash/workspace/generation gates, and atomic allowlisted primitives. Export payloads omit paths/content. Browser setup is unavailable without simulation.
- Project Foundry: the production TypeScript boundary validates exact DTOs while Rust owns ephemeral grants, path identity, destination absence, committed-object access, and the sole shared in-process `git2` renderer. Rust returns the complete plan body/internal bytes; TypeScript validates byte consistency, computes the digest, freezes the plan, and owns approval/presentation custody. Web core receives no template source/output or rendering authority. Fake selectors are harness-only and no native chooser execution is claimed. Cancel revokes every grant and retains no plan; production Apply is absent.
- XCOM 2 project recognition and diagnostics: convention scanning and activation-v1 configuration are jointly correlated but independently evaluated inside the authorized workspace. The convention scanner rejects symlinks, excludes fixed heavy directories, and enforces depth-8/20,000-entry bounds; pure two-kind evaluation prevents name-only, duplicate-kind, and one-kind false positives. The native-owned `.ide/xcom2.json` path accepts only strict UTF-8 exact-schema v1 within 64 KiB and 1–64 unique exact-case regular non-symlink contained roots. Duplicate/invalid/escaping input fails safely. Exactly eight safe codes map to fixed atomic warning copy with no project/native disclosure or edit/open/write action. Source `configured` and activation confidence `explicit` remain separate from recognition confidence; invalid config removes configured authority but cannot suppress strong Option A, whose existing activity mirrors the complete warning. Full Workspace Refresh clears old warning/decision, exposes neutral checking, and rejects stale results. The IDE never writes/reformats/deletes the project configuration or Option A evidence, mutates `.gitignore`, watches, or polls it; normal application-owned `.ide/workspace.json` marker/registry metadata is outside this input no-write assertion. Machine Settings remains separate. Manual confirmation/persistence, external roots, content parsing, general external-root grants, Build, Problems, Logs, language support, actions, bottom contributions, and external interactive setup remain deferred.
