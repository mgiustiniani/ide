# ARC42 — IDE Architecture Documentation

## Section 1: Introduction & Goals

### 1.1 Requirements Overview

The IDE is a three-panel Integrated Development Environment:

1. **Left sidebar** — accordion navigation with File Explorer above Workspace Explorer; both sections expand and collapse independently.
2. **Right/center area** — Monaco-only editor for opening and editing files.
3. **Editor-side tools and activities** — the bottom host contributes desktop Terminal plus a conditional project-scoped Problems tab, while the activity rail contributes the existing Files authority and the workspace-native Agent screen. The Agent screen contains Pi's real interactive TUI and read-only Changes, Activity, Resources, and Sessions accessories; web contributes Terminal only and no native Pi activity.

**CURRENT/AS-BUILT — 2026-07-16:** within application content, the activity rail and left sidebar span the full available height; the bottom shell/tool-window host belongs only to the narrower editor-side column and does not extend beneath navigation. Top-level chrome/status remains separate and stable through panel changes. The optional right sidebar remains inside the editor row and is responsively bounded. Keyboard resizing and accessible separator semantics remain available for the left and bottom panel boundaries. When the whole sidebar is collapsed, an accessible expand control persists in the activity rail; the bottom-panel toggle persists in the status bar in both visibility states. Desktop shell wiring routes both controls to layout state without clearing retained panel dimensions. The web and desktop declarations are now both `@implemented-and-validated`, with distinct target-specific evidence.

It runs as a **Tauri 2.x desktop application** and is reusable as a **standalone webapp** with no Tauri dependency.

Workspace Explorer lists every registered workspace and owns workspace switching, refresh, loading, and error feedback. The former duplicate workspace selector in the header has been removed. File Explorer compacts package-only namespace chains only beneath recognized Java source roots. It preserves the deepest real node/path, distinguishes production `src` and test folders, gives `pom.xml` a dedicated Maven icon, and leaves unrecognized directory hierarchies unchanged.

Monaco Editor 0.52.2 is the only file editor. It is bundled locally with same-origin workers, one model per file, and a Java Monarch/basic language contribution. Lazy activation waits for a visible, renderable, positive-area active-file host before mount and timeout; layout reruns after visibility returns. No-file state is a Kate-style create flow. Loading uses an inert source-free placeholder, and import/runtime failure offers Retry Monaco with no native fallback. No CDN or CSP expansion is required.

The implemented Java baseline has two desktop foundations. **Settings > Java** exposes only global full-JDK/JDT LS lifecycle/status and RefactorKit availability/version/path/capability discovery. Managed JDT LS now provides provider-neutral lifecycle, versioned document-sync, diagnostics, completion, hover, signature-help, and cancellation contracts; typed Tauri adapters; fixed no-shell Rust/LSP transport with isolated per-workspace data; and guarded Monaco providers. Fixed native RefactorKit Java scan/query/navigation handlers exist, but their project actions remain unexposed globally. Browser mode has no Java technology tab or hidden Java polling.

Interactive diagnostics, completion, hover, signature help, and cancellation operate only for the exact synchronized Java model. Workspace/session/path/URI/version/request/cancel guards, optimistic versions, serialized full-text `didChange` flush-before-request, and stale/late suppression protect the flow. Current diagnostics feed Monaco and a conditional project-scoped Problems tab; that visibility guard is not Java module activation. Completion maps only its primary edit; additional/workspace edits and commands are suppressed. Documentation is untrusted Markdown with HTML disabled, and managed configuration sets `java.signatureHelp.enabled=true`.

**2026-07-14 roadmap policy:** preserve and maintain this as-built lifecycle, synchronized-document flow, diagnostics/Problems projection, completion, hover, signature help, cancellation, and stale guards. Further IntelliSense or JDT LS expansion is removed from the active roadmap until a relevant released RefactorKit capability passes immutable real acceptance validation. Definition/references, symbols/hierarchy, code actions, formatting, rename, Java module activation, the full contextual Problems/Build/Tests/Logs lifecycle, general Java refactoring, and other contextual Java tooling are **UNSCHEDULED TODO / FROZEN HISTORICAL INVENTORY**, not milestones or target architecture. Unsupported or unintegrated capabilities are never simulated.

One bounded IDE workflow is implemented separately: **Paste Java Class from Clipboard** is available from a selected directory's context menu or `Ctrl/Cmd+V` while the directory tree owns focus; editor paste is not intercepted. Its coordinator capability-probes before an explicit clipboard read, presents complete backend placement, affected-file, rendered/structured-diff, risk, diagnostic, provenance/license, conflict, staleness, and blocker evidence, requires acknowledgement for unknown/high-risk provenance, applies only the exact approved ready plan under workspace/selection generation guards, displays the backend transaction, and refreshes/opens backend-reported paths. Rust manages one canonical-workspace, generation-scoped `bin/refactorkit-daemon` NDJSON process and supports preview, exact-plan apply, discard, and backend transaction rollback. Compatibility is provider-version-neutral: API 0.2 plus the required import/apply/discard/rollback method features authorize the current Java-import boundary; provider version is diagnostic only. Language-kernel and top-level safety metadata are strictly normalized and retained when advertised, but the four safety booleans may be absent and do not all gate current Java-import authorization. The IDE never parses or copies raw Java in presentation code, infers a package, writes files directly, falls back to target-package, logs source, or sends source/plan/transaction data to Pi. RefactorKit is the imported-project-content writer and rollback authority, but the current import UI has no rollback action. Missing or incomplete required method capability remains unavailable before clipboard read. See the [current Java boundary and frozen inventory](docs/JAVA_INTELLISENSE_PLAN.md); the retained research does not claim IntelliJ IDEA Ultimate parity.

## Section 2: Constraints

### 2.1 Technical Constraints

- **pnpm workspace** — all packages live under a single monorepo.
- **Node development-tool runtime** — the root manifest admits exactly `^22.13.0 || ^24.0.0 || >=26.0.0`. This is the intersection of Cucumber 13's `22 || 24 || >=26` contract with the active jsdom/ESLint visitor-key minimum of Node 22.13 on the Node 22 line. It constrains repository development commands; it is not evidence that every admitted Node version, browser, desktop runtime, or operating system has been validated.
- **Vite** — both `apps/web` and `apps/desktop` use Vite as the build tool.
- **Tauri 2.x** — desktop target requires Rust and Tauri CLI.
- **No Tauri imports in shared packages** — `packages/ui/`, `packages/web-core/`, `packages/contracts/` must not import `@tauri-apps/api`.
- **External Java import authority** — only a managed RefactorKit advertising API 0.2 and the required import/apply/discard/rollback method features may preview and apply a `targetDirectory` import or provide backend rollback. The IDE must not infer support from version, top-level safety metadata, or language-kernel discovery; convert a directory to target-package; or write a fallback patch. The current import UI has no rollback action.
- **Clipboard privacy** — capability probing precedes clipboard access; the clipboard is read only for an explicit directory-tree action and is never routed to Pi. Normal editor paste remains independent.
- **RefactorKit saved-snapshot operations** — semantic navigation and diagnostics must execute no project script and produce no workspace change, including hidden provider metadata. Advertised `writesWorkspace:false` is evidence to verify, not permission to tolerate a contradictory lock write. Diagnostics additionally requires strict schema v2, closed statuses, exact authority correlation, compiler/process attestation, exact UTF-16 ranges, complete bounded responses, existing-surface projection, and browser refusal.
- **XCOM recognition authority** — convention scanning is limited to the current authorized Linux workspace through a dedicated native metadata/name command. Exact-case regular entries are evidence; symlinks are neither traversed nor accepted. The fixed depth-8, 20,000-encounter, and heavy-directory exclusions are not caller-configurable.
- **XCOM activation configuration authority** — the native side alone owns `<authorized-workspace>/.ide/xcom2.json`. It accepts only activation-only v1 under strict 64 KiB, UTF-8, duplicate-key, schema, 1–64-root, exact-case, regular non-symlink, and canonical containment rules. Exactly eight safe codes may cross into fixed presentation; no raw project/native detail may cross. The IDE has no XCOM configuration/evidence write or `.gitignore` mutation authority and rereads only on explicit full Workspace Refresh. Normal application-owned `.ide/workspace.json` marker/registry metadata is outside that project-input no-write scope.
- **XCOM build-recipe inspection authority** — native begin owns opaque activation-attempt/root evidence handles and reserves one positive JavaScript-safe `inspectionGeneration` per attempt. The exact accepted authority retains that generation across repeated inspections; failed attempts consume reserved values, later accepted authority receives a later value, and exhaustion fails closed. Trusted TypeScript may acknowledge only evaluator-selected handles; Rust materializes exact active roots and synchronously revokes them on refresh, switch, failure, newer authority generation, cached restoration, and exit. Inspection remains token-free with `{ workspaceId, generation, moduleRoot }`; unchanged repeated reads return identical facts, while changed script/notice/conventional metadata preserves authority generation but changes bound facts/digest. Post-read stale checks remain. Provider-neutral asynchronous `consumeApproval(request)` has no production caller or executor; requested use removes authority before fresh exact inspection and can authorize only a fully re-reviewed digest-identical recipe once. It is request-time reinspection, not watch/poll. The contained `.scripts/build.ps1` remains untrusted metadata, and the capability has no process, network, write, SDK, game, prefix, proprietary-content, Deploy, Cook, Launch, or browser authority. `.ide/xcom2.json` v1 is unchanged.
- **Project Foundry authority** — one shared Rust in-process `git2` renderer is the sole Preview and Apply output authority and returns the complete plan body/internal bytes. TypeScript strictly validates the closed result and byte consistency, computes the digest, and owns immutable approval/presentation custody; web core owns no template source/output or parallel renderer. One-shot production Apply consumes frontend and native authority before destination validation. A present destination produces the bounded terminal `destination-present` refusal with preservation and no writes/residue; an absent destination may enter the Linux-only staged, journaled, fsync-durable, non-replacing transaction. Every pre-commit failure carries mandatory `cleanupStatus`, closed to `verified-complete` and `not-verified`; positive attestation requires conjunctively verified operation-owned cleanup plus final selected-parent durability, and only the exact stage-write positive tuple receives the separate fixed terminal alert. Fake selectors remain harness-only and provide no native chooser, GUI/E2E, or packaged-application claim.

## Section 6: Runtime Architecture

### 6.1 Startup Sequence

1. **Entry point** (`main.tsx`) mounts the React root and the app shell instantiates its runtime adapters.
2. **App component** (`App.tsx`) initializes stores and composes injected application and shell/document/editor controllers. Workspace-scoped auto-loads are deferred; the Pi Workspace Agent controller is mounted only by an attached docked or detached Agent renderer while its Rust process manager remains application-scoped.
3. **Workspace authorization transition** starts at positive generation 1. The Workspace controller awaits `ensureCurrentWorkspace`; no registry read or dependent native workspace read may overtake it.
4. **Registry promotion** lists the registry after authorization and promotes the ensured workspace over a stale or empty snapshot.
5. **Dependent activation** begins only after the authorized root and promoted registry are current: editor restore, file-tree load, Java attach/status load, legacy AI configuration/command metadata with session-message and run-trace projections disabled, RefactorKit status/capability discovery, and one jointly correlated XCOM convention scan plus fixed-path activation-v1 read run under the shared generation. With Settings closed, startup still performs no XCOM machine monitor, history, detail, poll, or subscription work.
6. **Panel layout** renders full-height activity/sidebar navigation, including Files and workspace-native Agent, beside an editor-side flex column. The editor row owns the main editor and optional responsively bounded right sidebar; the lower column owns the bottom resize boundary and tool host. Status and desktop top-level chrome remain outside application content. BottomPanel descriptors retain icon/title/scope/badge/disabled/active metadata and accessible tab/tabpanel keyboard behavior.
7. **Sidebar navigation** renders independently collapsible File Explorer and Workspace Explorer sections; Workspace Explorer lists registered workspaces and handles switching/refresh/errors, while File Explorer derives Java-aware presentation only below recognized source roots.
8. **Editor** renders a no-file create state or source-free loading placeholder; only a visible, renderable positive-area active-file host may start Monaco import/mount and timeout, followed by layout when visibility returns. Failure offers Retry Monaco.
9. **Legacy Terminal** setup is workspace independent and may proceed during root authorization; web shows a simulated session and desktop executes submitted commands one at a time. Interactive Pi is separate: its first Agent attachment occurs only after the Workspace Registry has authorized the exact active root.

If initial authorization fails, dependent workspace activation does not run, loading settles, and presentation receives a sanitized error. A later user switch invalidates an older cold-start attempt and advances the generation before collaborator reset/detach.

1. Advance `WorkspaceGeneration` before asynchronous detach or native switch work.

## Section 8: Cross-Cutting Concepts

### 8.1 State Management

- **Zustand** stores in `packages/web-core/state/`.
- Each panel has its own store slice (file tree, editor, terminal, panel layout).
- Stores are platform-agnostic; adapters update store values asynchronously.

- Shared Tailwind configuration lives in `packages/ui/tailwind.config.ts` and is consumed by app builds.

### 8.3 Error Handling

- Adapters catch platform errors and map them to user-facing error messages or typed adapter errors.
- View models expose loading and error state for UI handling where implemented.

### 8.4 Security

- Desktop: Tauri uses the default capability and a Content Security Policy; Rust commands constrain file paths to the workspace and reject shell chaining, raw shells, executable paths, long-running commands, and oversized output.
- Monaco and all editor workers are local same-origin assets; the editor adds no CDN dependency and requires no CSP expansion.
- Webapp: runs in the browser sandbox and stores simulated workspace data in `localStorage`.
- Managed JDT LS: Rust authorizes workspace paths, discovers known external tools, starts JDT LS without a shell, isolates per-workspace state, and bounds messages/events/restarts/cleanup. Exact-model workspace/session/path/URI/version/request/cancel guards and flush-before-request ordering prevent stale or cross-model results. Completion suppresses additional/workspace edits and commands; Markdown is untrusted with HTML disabled. Browser adapters report Java providers unavailable rather than simulating results; a remote provider would require explicit opt-in and a separate ADR.

Language-kernel and top-level safety metadata are validated and retained when advertised but are not all authorization gates. Unsupported, stale, refused, blocked, mismatched, or failed work stops without fallback. Clipboard source is transient, goes only to RefactorKit preview after support is proven, and never reaches Pi.
